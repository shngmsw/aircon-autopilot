# Jev 比較記録と停止待機の検証

2026-10-07 実施。本番へアクセス・配備・操作せず、制御サイクル内のRemo・天気をモックして評価した。
機械可読の集計は [simulation-results.json](simulation-results.json)。

## 再現

リポジトリ直下で実行する。既定では外部APIを呼ばない。

```bash
.venv/bin/python -m pytest -q
.venv/bin/python scripts/simulate_control.py --output /tmp/simulation.json
# 実履歴の読み込みは任意。個人の履歴ファイルはコミットしない。
.venv/bin/python scripts/simulate_control.py --history /path/to/history.json --output /tmp/replay.json
# TYPESAFE_API_KEY が設定済みの場合のみ、架空履歴を使った6件の比較判断を追加する。
.venv/bin/python scripts/simulate_control.py --jev --output /tmp/jev-simulation.json
```

## 仮定と測定方法

各ケース8時間、10分間隔の制御、1分刻みの温度更新、目標帯21〜24℃。
室温は外気との熱交換、内部/日射の発熱、冷暖房、暖房停止後の減衰する余熱から計算する。
係数は架空で、実部屋の熱特性へのフィッティングはしていない。
設定温度に届けばモデル上の冷暖房能力は休止する。
保持時間10分・切替待ち60分・機種の温度丸め・SQLiteへの状態保存は実際のcontrollerを通す。
対応モードはcool/warm/blow、湿度55%。既存の送風判定を無効にし、停止待機の差だけを比較する。
送風有効時に停止待機が優先されることは別の回帰テストで検証する。

「稼働分」は仮定した熱モデルで冷暖房能力が働いた分数であり、実消費電力や実機コンプレッサーの測定値ではない。
「再起動」は運転設定の変更ではなく、停止から電源ONになった回数。
目標帯逸脱は1分ごとの室温で数える。安全違反の集計は欠測・手動停止中の操作の有無。
冷暖房切替待ちは暖房余熱のケースと既存の結合テストで確認する。

## 結果

表は「既存 → 変更後」。Jevはこの温度推移を操作せず、比較判断だけ行う。

| 架空ケース | 目標帯逸脱（分） | 最大逸脱（℃） | モデル稼働（分） | 再起動（回） |
|---|---:|---:|---:|---:|
| 自然に冷える | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 |
| 断熱が強く内部発熱がある | 0 → 7 | 0 → 0.03 | 67 → 40 | 0 → 1 |
| 日射で上がる | 0 → 51 | 0 → 0.11 | 198 → 160 | 0 → 4 |
| 外気が暖かい | 0 → 0 | 0 → 0 | 136 → 136 | 0 → 0 |
| 冬の暖房 | 59 → 59 | 1.47 → 1.47 | 130 → 130 | 2 → 2 |
| 暖房停止後の余熱 | 63 → 63 | 0.26 → 0.26 | 33 → 30 | 1 → 1 |
| センサー欠測 | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 |
| 手動停止 | 0 → 0 | 0 → 0 | 0 → 0 | 0 → 0 |

8ケースで欠測・手動停止中の操作違反は0件。暖房と外気が暖かいケースの指標は同じ。
一方、停止待機によって日射ケースの電源再起動が4回に増え、快適性とのトレードオフが残る。
実測の省エネ改善は主張できない。元々コンプレッサーが休止していた場合、節電幅は小さい可能性がある。

最初の「上限+0.7℃まで待つ」案では、断熱ケースが156分・最大0.73℃、
日射ケースが313分・最大0.81℃逸脱したため採用しなかった。
最終版は停止へ入る境界を上限-0.7℃、停止を解除する境界を上限にする。

## 実履歴の再評価

アップロードされた24時間の144行のうち、最初の行を除く143時点を評価した。
各時点は当時の目標帯、前時点の電源・モード・設定温度、当時の室温・外気で評価し、
未来の行の目標設定や温度を参照しない。64時点で停止待機が既存の冷房判定と異なった。
該当期間は2026-10-07 00:03〜10:34 JSTで、外気19℃台・室温約22℃の時間帯。

これは一時点ずつの推奨比較。保持・切替・機種設定は履歴から復元できず、
停止後の代替室温を実履歴から推定したものではない。
13:15・16:05の帯内での再開は外気24.3℃だったため、この寒い外気向けのルールでは変わらない。
このケースを含む汎用的な方針改善はJevの比較評価を続けて判断する。

## Jev の実API評価

モデル `jev-1.13.0`。6種類の架空履歴の最初の1時間を入力にし、1件ずつ比較判断した。
自然冷却・断熱・日射・外気が暖かい・冬暖房は現状維持、暖房余熱は信頼度33%の冷房提案だった。
欠測・手動停止ケースはAPI送信をスキップした。結果の確率・信頼度はJSONに保存している。
当初はモデル名`jev-1.13`が400だったため、正式IDへ修正済み。

Jevの入力には既存判定が含まれるため、それに引かれる可能性がある。
冷房継続中の履歴から停止後の温度推移が分かるわけでもない。
現時点ではJevの優位性や、この部屋での信頼度の校正は確認できていない。
実機への反映はせず、まず比較記録として運用する。

## 本番へ進める条件

PRレビュー後も、Jevは`JEV_MODE=shadow`で比較のみ。
既存制御を維持してJevの記録だけ収集する場合は`PASSIVE_WAIT_ENABLED=false`を明示する。
停止待機の実制御を試す段階で初めて有効化する。本番で同時に2つの制御プロセスを動かさない。
室温の逸脱と停止・再起動の頻度を確認し、問題があれば`PASSIVE_WAIT_ENABLED=false`へ戻す。
